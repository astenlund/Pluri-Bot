# Bugs (history)

Paths under `development/` or `development\` in this file name the frozen local archive in the LocalAppData folder the project came from; they are not part of this repository.

Fixed bugs, archived from `BUGS.md` so the active list stays scannable. **Archaeological**: read only when consulted. When a bug is fixed, append its entry here rather than to the active file.

The bug breakout file at `bugs/<slug>.md` (when present) stays in place as the historical diagnosis record; the entry here is a brief description of the fix and the commit it landed in.

## Cross-reference resolution

`/nightshift:ready` does **not** parse this file for work; it reads it only for the line-discipline check and the link checks, which verify links into it and count its links as keeping the records they name reachable. When a bug is fixed, every other `**Requires:**` line in `FEATURES.md` / `BUGS.md` that referenced it is edited at the same time to drop the now-satisfied reference (mirror of the `FEATURES.md` convention). The active `Requires:` lines therefore describe what is *currently* blocking; this file is purely archaeological.

### A mission id naming a Windows device cannot launch once it declares a machine or knowledge store

Fixed in bootstrap v58, published at gist revision `04410eeb0beab47fccf27161731d462dc8930d96` (SHA-256 `13fe6144ee3b2555878db239230101ce1403a21753578ae2e7f44bbd50a0c4a6`). The strict reading of `PROJECT.json` now refuses a Windows device name (`con`, `prn`, `aux`, `nul`, `com1` to `com9`, `lpt1` to `lpt9`) as the `mission_id` of a mission that declares any store, saying why, so a v58 engine reports such a package as damaged and none of its writers produces one; a package on an earlier engine is unaffected, since only the DLSS package updates its engine. The release suite case 'mission stores refuse a Windows device name as the id of a mission with stores' covers it. The refusal still reaches the user inside the generic damaged-package message; the user deferred that at review. Whether `com0` and `lpt0` resolve to devices on older Windows builds is unchecked; on build 26300 only `nul` resolved to a device. Evidence: `development/v57-stores/minors-triage.md`, `development/v58-store-fixes/`.

### Game fingerprint changes when a session adds an executable to the game folder

Fixed in bootstrap v61, published at gist revision `83565d1c3754416d08ed3882f82205f6ef521696` (SHA-256 `35d5c9eaebe93276a3b70d94bf8ea92bc5bdb7ce70346606facdcfc8ef45f6aa`). A location record or game notes holding the fingerprint over a subset of the current qualifying executables (any subset while there are at most ten, beyond that the sets with one or two removed, and always the eight largest) is now accepted and kept rather than widened (outside task sessions, game notes are brought to the fingerprint the location record keeps), so a game whose folder gains an executable, such as a helper a mod installs, still launches and matches again once that executable is removed; `Resolve-Dlss5GameFingerprint` applies the rule in the wrong-directory guard, the moved-location orphan matching, the location record step, the Stores view and Clear. No migration was needed, since records already holding the narrower fingerprint are exactly what the subset rule accepts. Observed on Resident Evil 7 on 2026-11-15, whose stored fingerprints the stopgap had rewritten to the wider value that included `gitc-uplift-helper64.exe`; v61 accepts that value only while every executable it covers, the helper included, is present, so removing the helper would refuse it as before. `tests\Test-DLSS5Fingerprint.ps1` and the interop case for a game that v60 recorded before a mod added an executable cover it. A deferred minor from the v61 code review, the cost of the subset search in a folder with many executables, is tracked as its own bug in `BUGS.md`. Evidence: `development/v61-fingerprint-subset/`.

### A mission merge does not say at run time whether it is three-way or two-way

Fixed in bootstrap v62, published at gist revision `045d17810cd2861878a84d6450962ce403272786` (SHA-256 `f7104237e6db9e24e5b06407d64cd83d8ddf09a4f7c9437cb5ceb02dc2f45239`). Before its `Starting <host>` line, `Invoke-Dlss5MissionMerge` now states the mode it runs from the ancestor it read under the bootstrap lock: a three-way merge with the mission the edit replaced, or a two-way merge with the reason that mission is not available, so a merge whose ancestor another window cleared after the what's-changed box was shown says it runs two-way. The release suite case 'merge states the mode it runs, two-way once the ancestor was cleared after the box described a three-way merge' covers it. Evidence: `development/v62-merge-messages/`.

### A merge reports a failed prompt write as "the AI host could not be started"

Fixed in bootstrap v62, published at gist revision `045d17810cd2861878a84d6450962ce403272786` (SHA-256 `f7104237e6db9e24e5b06407d64cd83d8ddf09a4f7c9437cb5ceb02dc2f45239`). `Invoke-Dlss5InteractiveAgent` now records whether every prompt file of the launch was written and the innermost message of a failure it caught, and a merge stopped before the host ran says "the merge prompt could not be written to <scratch folder>" or "the AI host could not be started", each with its cause, before "Nothing was written."; a failure after the prompt write but before the host starts still counts as the host not starting. ### Game fingerprint subset search is slow in a folder with many executables

Fixed in bootstrap v63, published at gist revision `4e66a092f105da76c574f728db1391f81d54cb05` (SHA-256 `fce07678e1823cb30eada6cd1a9089d483d587dfa5ee44c9153696ec87a3875b`). `Resolve-Dlss5GameFingerprint` now takes the location record a fingerprint came from and skips the subset search when `Test-Dlss5RecordNamesOtherGame` finds that the record's `game_name` names another game, by that name (compared lowercased, as the fingerprint material is) or by its `steam_appid`; a record without a `game_name`, which no session writes, and game notes are searched as before. The search itself now runs in a compiled helper (`Dlss5FingerprintNative`, compiled on first use) over the same sets v62 built, with the same material. Measured on this machine over synthetic identities, the search took 349 ms, 1532 ms and 5199 ms at 60, 120 and 250 executables in v62 and 6 ms, 58 ms and 187 ms in v63. The release suite cases 'fingerprint session plan skips the subset search for an orphaned record of another game', 'fingerprint search still finds a subset record of this game as a session writes it, and skips one that names another game' and 'fingerprint compiled subset search builds the same sets as the PowerShell construction it replaced' cover it. Evidence: `development/v63-fingerprint-speed/`.

### v64 notes validation: deferred review minors

For the `dlss5` mission with the target store declared, `--internal-notes-validate` now reports `{"outcome":"missing"}` when a guarded snapshot positively finds no game notes file, instead of damage; a path that cannot be inspected or holds something other than a readable notes file is still damage, and the session end is unchanged. The documentation slips are corrected in `development/v64-notes-validate/consumers.md`, the v64 design and the composable builder record. The release suite case 'mission stores notes validation reports absent game notes as missing, which a task session leaves uncreated' and the generated-prompt case 'prompt defines complete target display records' cover it. The review's deferred minors are tracked as [v65 notes missing outcome: deferred review minors](bugs/v65-notes-missing-review-minors.md). Evidence: `development/v65-notes-missing/`.

### Game-notes writes in instruction files lack an absent-notes branch

Fixed in bootstrap v67, published at gist revision `858ae4c6efe62fc2180eb5f040f8e7e2697668ec` (SHA-256 `35414382fc84514ea47197d5bdb2d01f158b33ecf6d6b8c854cfd3ee99a92140`). The mission's game notes rules (operating rule 7) now carry one absent-notes rule, directly after the notes validation rule: where no game notes file exists in a session that must not create one, nothing is recorded in the game notes, and for every record the prompt or an instruction file would keep there, the agent tells the user what it would have held. The research rule keeps only its own part, telling the user which sources the research checked, and v66's own absent-notes sentence is retired. The three instruction file write sites point at the rule by name: the local runtime build's verification record in `INSTRUCTIONS.local-runtime-build.md`, and the declined offer and the interruption evidence and status in `INSTRUCTIONS.settings-optimization.md`; the third was found while investigating the bug. The generated-prompt case 'prompt defines complete target display records' covers the rule and the pointers. The review deferred two minors without tracking them: `INSTRUCTIONS.cleanup-boundary.md` records retained paths in "the applicable session notes" with no pointer of its own (the general rule covers it where those are the game notes), and the decline sentence in `INSTRUCTIONS.settings-optimization.md` could be read as attaching "starts no settings research" to the absent-notes branch alone. Evidence: `development/v67-absent-notes/`.
