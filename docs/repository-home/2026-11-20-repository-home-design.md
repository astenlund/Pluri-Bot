## Versions

### The pair

From v1-1 a package is identified by the pair `v<engine>-<mission>`. The engine version belongs to Pluri-Bot and names one engine; the mission version belongs to the mission's repository and names one published mission. Each half's number moves only when that half changes, so a mission-only release needs no Pluri-Bot release, and an engine release needs no mission change. Pluri-Bot's hello-world base carries its own pair, its mission half on the hello-world mission's own numbering; it ships only with a Pluri-Bot engine release, so a hello-world-only change waits for the next one. Pluri-Bot tags its releases `v<engine>` (such as `v2`), and DLSS5-Bot tags the pair (such as `v2-1`). The numbers v1 to v67 of the earlier line are legacy versions: durable text that names one calls it legacy (`legacy v67`), and Pluri-Bot tags the imported engine `legacy-v67`, so no new tag can collide with an old number.

Each number names exactly one set of bytes: an engine version always has the same engine hash, and a mission version always has the same mission hash. A published version is never published again with other bytes, and a fix after publication takes a new version; a version whose release was never published may be tagged again once its draft and tag are removed, the tag deletion confirmed by the user. Release tooling refuses a release whose engine differs from the engine its pinned version names, or whose mission version was used by any earlier release with a different mission hash.

The mission version is part of the mission content, held in `PROJECT.json`, so the mission hash covers it and the engine hash does not. A mission without a mission version, such as one whose absorbed `PROJECT.json` carries none, shows its number as `?`. A Merge result written as an edit carries the release's mission version and is primed as an edit of it; a Merge result equal to the release's mission is written as Take, as today, and shows the release's mission version unprimed.

### Display

The menu header, the what's-changed box, the README and the release notes show the pair as `v<engine>[']-<mission>[']`. A prime on the mission half marks an edited mission, taken from the copy's existing edited-mission state, as the engine maintains it today: `v1-1'`. That flag is the display's predicate only; which update path a copy takes still follows today's comparison of its published-form hash with the trust record, apart from a local engine's Take and a copy without a verified own DLSS release, which Local engine changes and Updating and release order set out, so a copy whose absorbed files equal the published mission shows a prime yet takes the whole-file update, which loses nothing. A prime on the engine half marks an engine that is not a release's: a dev build, taken from a mark assembly sets on a build from a dirty Pluri-Bot tree or from a commit other than the declared release-candidate commit, or a local engine as Local engine changes describes it: `v1'-1`. Both can apply: `v1'-1'`. The display describes what the copy holds, while an update always applies one published release; the displayed pair is never a trust key.

A release candidate is built from the clean commit that will be tagged, so it is unmarked: review and the full checks clear exactly those bytes, Pluri-Bot then tags that commit, and the release workflow's rebuild from the pin is byte-identical to them. The mark changes package bytes, so a marked package must never establish trust a genuine release would later collide with: marked builds run only in isolated test stores, as candidates do today, and publication refuses them, as it refuses a package with the local mark. The engine finds its store only through `LOCALAPPDATA` and cannot tell a redirected store from the real one, so the test harness creates a marker file at the root of each isolated store, and a marked package writes trust only in a store holding that marker.

### Updating and release order

Copies update to the latest release as a whole. Both halves reach every copy in the same update, and the launch that applies an update runs the applied engine and mission: it re-executes whenever the engine bytes it applied differ from the running ones, not only when the engine version rose as today, so a Take over a local engine at an unchanged engine number also runs the release's engine. An unedited copy gets both applied directly, as today's whole-file update. An edited copy gets the engine applied automatically, as today's engine-only update, and in the same update the what's-changed box offers the release's mission whenever it differs from the published mission the edit replaced or that one is unknown, as the engine decides it today: Merge, where the AI host combines the copy's edits with the release's mission and shows the result before anything is written, Take or Keep. A release whose mission equals the one the edit replaced offers nothing, since Take would only discard the edits and Merge would return them. A mission-only release reaches an edited copy the same way, its engine unchanged.

A copy's own release is the release it last applied, which its displayed pair does not always show. Update ordering and adoption key on it, defined as follows:

- An unedited copy's own release is the pair the package embeds, provided this machine holds a pair record its bytes match. Without one, as for a locally assembled draft or a copy first used offline, it has no verified own DLSS release until such a record is written, as when its worker finds the latest release's verified bytes equal to its own.
- An edited copy, or one running a local engine, keeps its own release in a record in its STATE. The copy's first mission content write or first local adoption, whichever comes first, sets the record to the copy's verified own release just before that write, or to a no-DLSS-release value when it has none. Every applied update rewrites the record; acknowledgement, Keep, later mission content writes and further local adoptions keep it. This record is what stops an edited copy that kept its mission across a mission-only release from being offered that release again.
- The record holds a DLSS release only. A mission content write that turns a copy of another mission into a DLSS one, whether its first write or a later one, as an absorb of a DLSS mission into the hello-world base does, sets the record to the no-DLSS-release value, since the copy's pairs so far belonged to another mission's numbering; later writes, relaunches and Keep keep that value, and the pair the package embeds never overrides it.
- A copy without a verified own DLSS release compares only the engine half until it first applies a DLSS release, taking one whose engine is not lower than its own. Its mission counts as edited when its mission hash differs from the release's, so it is kept and offered for replacement under the usual rule above, and adoption checks a candidate against the engine version it embeds.

Only copies of the DLSS mission update from DLSS5-Bot; a package of any other mission, the hello-world base among them, never updates automatically, as only the DLSS package updates today.

Releases are ordered by the pair itself, so they need no number of their own: across releases neither half ever goes backwards, and every release raises at least one half. Publication refuses a release that is lower than the highest pair among all published releases in either half, or equal to it in both. The engine half never goes backwards because an older engine refuses state a later engine may have written (an unknown STATE schema or key, `ConvertFrom-Dlss5StateBody`); the mission half never goes backwards so that the pair alone orders releases, and returning to an earlier mission takes a new mission version. A copy applies a release only when it is at least as high as the copy's own release in both halves and higher in one, and the engine refuses a release lower in either half than the highest it has recorded, as it refuses an unrecorded engine at or below its recorded maximum today. Unlike today, that engine maximum is kept per mission (user decision, 2026-11-21): each mission's packages protect their own engine history, so a package of another mission on a newer engine, the hello-world base or any derived variant, never blocks a DLSS release pinned to an older engine, and no derived variant has to keep up with the engine. The engine records themselves stay shared, since an engine version names one engine hash whichever mission carries it. Each mission keeps, beside them, its own history of the engine versions its packages have been admitted on, and its maximum is the highest of those; an engine version at or below that maximum is admitted for the mission only when the mission's own history holds it, so an engine another mission recorded does not lift the refusal. Every path that admits an engine for a mission adds it to that mission's history, except that for the DLSS mission only a copy with a verified own DLSS release adds to it: a copy without one, such as a hello-world base turned into a DLSS copy by a content write, is judged by the DLSS history but does not raise it, so a newer-engine variant carrying the DLSS id never blocks DLSS releases pinned to an older engine. A copy whose mission a content write changes is judged by its new mission's history. The engine record and the history entry are one trust write, resumable like the others. Today's validation of an edited copy's retained mission by the incoming release's engine stays, and its refusal still skips the update with the edit intact. Updating rests on one property, which every engine change must keep: an engine runs every mission an earlier engine ran, which the engine-only update already relies on. Missions carry no minimum engine field.

### Trust

v1 starts with a fresh trust store: it keeps its trust in records of its own and neither reads nor writes the legacy trust records (the legacy trust maps, their recorded maxima and the machine-notes mirror), which the switchover moves aside so that nothing reads them. v1 changes no runtime-state format (user decision, 2026-11-21): apart from trust, which starts fresh, the runtime state (machine config, the engine store's probe results, location records, notes, the mission stores and ancestors) carries over as it is into `%LOCALAPPDATA%\Pluri-Bot`, moved there by the switchover, and v1 reads it unchanged. The per-launch update channel between a launch and its background worker, under `sessions\<launch id>`, is scratch, not carried-over state: v1 writes the current and staged releases in it as pairs, which the update notification shows, the current one as the copy's engine version with no pair where the copy has no verified own DLSS release, as Updating and release order defines, and treats a channel file a legacy launch left as stale (user decision, 2026-11-21).

The engine file carries no legacy marker lines, and the engine hash is computed over the engine as the engine file holds it, so the engine file's SHA-256 is its engine hash and equals the engine hash recovered from any package built from it. Engine trust maps each engine version to that hash, and whole-file trust maps each published DLSS pair to its published hash; as today, whole-file trust is written for DLSS packages only, since a pair is unique only within its mission and the hello-world base can share a DLSS package's pair. A later fetch of a recorded pair or engine version with other bytes is the existing integrity collision. Every path that writes trust (among them staging, first use of an engine, seeding or promoting the canonical copy, adoption and canonical installation; the property covers every such path, not only these; a local engine's adoption writes only its local-engine record, as Local engine changes sets out) writes only the records it is entitled to: a path that admits an engine writes the engine record, and a pair record comes only from bytes verified as a published DLSS5-Bot release, through staging a fetched release, the release procedure's install after readback, or a worker finding the latest release's verified bytes equal to its own copy's, never from an edited copy or a locally assembled package, so a genuine release cannot later collide with a hash recorded from an edit or a draft. First use of a package whose pair has no record, offline included, writes at most the engine record and the mission history entry its engine is entitled to, as Updating and release order sets out, and no pair record. Only bytes with a pair record ever fill the canonical slot, which therefore only ever holds a published DLSS release, as the feature record settles: a package without one runs as a game copy but is neither seeded into an empty slot nor offered for promotion, and the slot later takes the genuine release at that pair as any release. Each write is resumable: a state with some of its records written completes the missing ones its own path was entitled to, from the same bytes, when the present ones agree, and fails closed when they disagree.

### Local engine changes

A user can still change the engine on their own machine without waiting for a release, as an approved bootstrap change in a game session does today. From v1-1 such a change is a local engine: it keeps the pair of the release it was built from, so it never claims a version a release will use, and adoption (`--internal-adopt-bootstrap`) accepts it at that same pair. A local engine is adopted into the game copy only: unlike adoption today, which writes the shared canonical copy before the game copy, the canonical copy stays the published release that other copies update from, and another game that wants the change adopts it separately; adoption of a local engine refuses the canonical slot as its target. Adoption refuses a candidate whose engine version differs from that of the game copy's own release, with a message stating this rule; the mission half is not compared, since adoption of a local engine keeps the game copy's mission, edited or not, unlike adoption today, which replaces an unedited game copy's mission with the candidate's. A game agent following older bootstrap-changes instructions, which bump the version, is thus stopped and told the current rule. Adoption trusts a local engine through a local-engine record keyed by its engine hash, which no release path writes, and writes no engine-version record and no pair record for it, so a later release can never collide with it. It does not carry the engine mark, which stays for builds from a dirty Pluri-Bot tree or another commit and confines them to test stores; a local engine runs in the real store. It carries a local mark instead, which the engine's assembly sets when asked for a local build; adoption never stamps it, so the approved hash is the candidate's own, and adoption refuses a candidate whose engine differs from its engine version's release record but carries no local mark, since its own startup would refuse it. Both marks lie outside the hashed engine text, so a package's engine hash is that of the engine it was built from whatever marks it carries, and the local mark identifies the package as local on any machine: a package with the local mark never writes an engine-version record or a pair record for its own bytes on any path, first use included, while as an update worker it still records trust for a release it fetched and verified, as staging does today; on a machine without its local-engine record, such as after the game copy is moved to another machine, it is refused as untrusted with a message saying it must be adopted there. Its engine half shows primed (`v1'-1`), taken from the local mark. The mission's bootstrap-changes instructions are rewritten in v1-1 to describe this, dropping the version increments, and the Git rules of `MISSION.md` and the engine's Git preflight that implements them are brought into agreement with it: a modified tracked updater whose engine matches its local-engine record is admitted as the bootstrap's own write, as one matching the engine record of its version is today, and the engine backup joins the updater, the game notes and the `.bkp` in the set of files the bootstrap owns, so every consumer of that set handles it, the Git rules (where it may be untracked) and the session snapshot of a non-Git game folder (where it is excluded from the game's changes) among them. A local build needs only the game copy: the engine can write its own engine form from any package it runs, so a game session assembles a local candidate offline, without a Pluri-Bot clone.

When a newer release arrives for a copy running a local engine, it is not applied automatically: the what's-changed box offers Take the release or Keep the local engine. Take applies the release as any update would, except that the mission counts as edited only when its mission hash differs from the published mission of the copy's release, since the local engine alone changes the published-form hash that the update path compares: an untouched mission is replaced by the release's, and a genuine mission edit gets the usual mission offer. Adoption records that published mission's hash in the game copy's STATE, so the comparison never depends on the canonical copy, which another game may have advanced since. It records the copy's own mission hash when the copy's published form, armed or not, matches its release's whole-file record, as the existing published-mission check establishes. A later adoption at the same release keeps the hash an earlier one recorded, since the local engine itself now fails that check. In every other case the hash is unknown, because the mission an edit replaced can belong to an earlier release. An unknown hash counts the mission as edited: it is kept, and the mission offer follows the usual rule in Updating, so nothing is replaced unasked. A first mission edit on a local-engine copy whose mission still has the recorded hash records that mission as the one the edit replaced and keeps it as a merge ancestor, as the first edit of a published copy does today, where today's whole-file check would fail because of the local engine. Take keeps the local package in its own engine backup beside the `.bkp`, written before any other step and replaced only by a later Take over a local engine, under the same Git rules as the `.bkp`, so the mission steps that follow keep using the `.bkp` as today without losing the local engine. Keep skips that release, recorded in the game copy's STATE so the same release is not offered again while a newer one is. Where no user can answer, as in a task session or an unattended launch, the local engine is kept and the release is offered at the next interactive launch.

## Assembly

From v1-1 the engine assembles packages itself, through an `--internal-assemble` entry point: given a mission folder and the build kind (a release build, a dev build as Display defines it, or a local build as Local engine changes defines it), it embeds the mission with an empty STATE section, sets the engine mark on a dev build and the local mark on a local build, writes the package in published form, and confirms the result with the strict identity check. It is the inverse of Explode and a thin dispatch over the section functions the engine already ships for absorb, Explode, the updater and the merge, so the format has one implementation. Absorb is not used: it is the user's edit operation, needs a package with a `PROJECT.json` to start from, and writes edit state rather than the published form.

The entry point runs from the engine file, which has an empty MISSION section and so is not a launchable package. The engine accepts its own engine form for this one mode and refuses every other mode on it. Assembly is a pure function of the engine bytes, the mission files and its arguments: it reads no trust, takes no guard and writes nothing outside its output, so it runs the same on the release runner and locally. The join of the wrapper and `payload.ps1` into the engine file stays a Pluri-Bot build step, since it produces the engine; besides it, any package can write its own engine form, without marks, as Local engine changes relies on for a local build. Step 1 still assembles with the legacy v67 engine, which has no such entry point, so until v1-1 both repositories assemble through the carried `Assemble-Package.ps1`, a copy in each, and v1-1 retires both copies; where this design says a repository assembles by running the engine's assembly, that holds from v1-1.

## Step 1: repositories and import

### What each repository holds

Pluri-Bot holds the engine in exploded, split form: the batch wrapper and `payload.ps1` as separate source files, joined at build time into the engine file; the hello-world mission as loose files, which the joined engine assembles into the hello-world base; and the engine's release tooling. A Pluri-Bot release publishes the engine file with its SHA-256 and the assembled hello-world base, named `Pluri-Bot.cmd` from v1.

DLSS5-Bot holds the DLSS mission as loose components in the layout Explode writes (from legacy v67's `mission-dlss5\`), the vendored engine file with its pin file, the release suite and its helpers from `tests\`, the prompt parity tooling, the live host probes, and from step 2 the interop suite and the publication tooling. It builds the package by running the vendored engine's assembly. The release suite stays in DLSS5-Bot, because it tests the shipped DLSS package, apart from the cases that read the hello-world base or the hello-world mission, which Pluri-Bot owns: those move to Pluri-Bot in step 1 and run there against its own base, beside the hello-world base's own test (user decision, 2026-11-21). The new cases that combine the hello-world base with DLSS behavior (a shared pair, a newer DLSS release, an absorb of a DLSS mission into the base) also run in Pluri-Bot, with a minimal fixture mission declaring the DLSS mission id in place of the real DLSS mission, since the DLSS-specific behavior keys on that id. Moving the other engine cases into Pluri-Bot is later work, tracked as its own backlog entry at migration.

Historical packages that tests read come with the suite: the legacy v22 and v49 packages that `tests\Test-DLSS5Package.ps1` reads, and the legacy v67 package, which serves as v1-1's baseline, are committed under `tests\fixtures\` with their SHA-256. The import's record names, for each, the gist revision that published those exact bytes, which is what makes them already public. The standalone v23 and v24 suites and the v23 hand-off in `Test-DLSS5Adder.ps1`, which no current release reaches, retire, and the import's record says why. From v1-1 on, the baseline and interop runs obtain the previous release's bytes by reassembling its tagged commit or downloading its release asset, and require them to match the hash that release published. The first DLSS publication of the new line, normally v1-1 and whichever engine it pins, has no previous release, so its baseline is the legacy v67 fixture and its interop suite is empty, since no copy updates to it. A previous release that failed its readback or its live check cannot supply a valid baseline or be expected to update itself, so its successor's release record names it as such, and the successor takes as its baseline and interop predecessor the latest release that passed both, or the legacy v67 fixture and an empty interop suite when there is none; after a failed live check, the successor's install over the failed release in the canonical slot, verified by readback, stands in for that release's previous-updater cases. The retained suite must run with the `development\` archive unavailable.

The release-folder scripts are per-release copies today, with version, hash and revision constants rewritten for each release. In the repositories each script exists once, and the per-release values (the pair, the baseline, the previous release) come from one release record per release, so a release changes data, not script copies. Which scripts survive, merge or retire is the implementer's to settle and the reviewer's to check, with one constraint: every check the legacy v67 release procedure runs keeps an equivalent, or its retirement is stated in the import's record with the reason. Step 1 imports and generalizes the scripts its own checks use or that no release ties to its numbers (the suite runners, the filtered suite, prompt rendering and parity, notes validation, the launch function comparison and the live probes); the scripts only a release runs (candidate build and verification, the baseline runner with its carry rules and their tests, installation, the post-review checks, the interop suite and the gist publication scripts) stay in the archive until step 2, which converts each for the v1-1 procedure or records its retirement (user decision, 2026-11-21).

### The vendored engine and its pin

DLSS5-Bot commits the engine file and a pin file recording the engine version, the Pluri-Bot tag and commit, and the engine hash. A pin update script fetches a chosen Pluri-Bot release, checks the engine file against the hash that release publishes, and rewrites both files, so an engine update is one reviewable commit. There are no submodules, and assembly works offline from the committed files.

A candidate under development needs an unreleased engine, so DLSS5-Bot's tooling also takes the engine from a local Pluri-Bot working tree for building and testing, recording that tree's commit and whether it was clean; a build from a dirty tree, or from a commit other than the declared release-candidate commit, carries the engine mark. The release candidate is built from the clean commit that will be tagged, reviewed and run through DLSS5-Bot's full checks; Pluri-Bot tags that commit only after they pass, and the tagged engine must hash identically to the tested one, so a Pluri-Bot tag always marks an engine that was tested inside a DLSS package, and the DLSS package built from the pin is the one that was cleared. Publication refuses a DLSS package whose engine is not the pinned engine of a tagged Pluri-Bot release.

Step 1 pins a Pluri-Bot `legacy-v67` release of the legacy v67 engine, so that the pin and its update script are proven before v1-1. That engine file keeps its legacy markers, since its engine hash, the legacy definition, covers them. The `legacy-v67` release is made by hand, with the user's go-ahead, since the release workflows arrive with step 2: its files are the joined legacy engine and the hello-world base, each read back from the published release against the hashes step 1 acceptance establishes.

### Backlog split

Each repository keeps its own `.nightshift` backlog. Each entry goes where its code lives: engine work to Pluri-Bot, mission work to DLSS5-Bot; an entry that spans both goes to Pluri-Bot, with a pointer entry in DLSS5-Bot. The history indexes and the feature record of the Composable AI bootstrap builder go to Pluri-Bot, with pointers from DLSS5-Bot. After the split, `/nightshift:ready` must parse both backlogs with no structural errors, and the backlog here is reduced to a pointer at the two repositories rather than deleted, so a later session started here finds them. This design and its triage record (`spec-triage.md`, without the review briefs and reviewer transcripts, which stay in the archive) go to Pluri-Bot with the feature record, under the privacy sweep, which then links to them there. They stay editable in Pluri-Bot until step 2 ships, and their copies in this design's archive folder are frozen. In every backlog file the split moves, a link into `development\` (earlier designs, probe records, release folders) is kept as a reference to the local archive and marked as such. The import's record lives in each repository for its own half, and each release's record in the repository whose release it records.

### Instruction files

The repository instructions (layout, release procedure, publication) move from `%LOCALAPPDATA%\DLSS5-ADDER\AGENTS.md` into each repository's `AGENTS.md`, each keeping what concerns its own code. Because the repositories are public, those instructions become public; they describe procedures, not credentials, and publishing still needs the author's GitHub access. The AppData `AGENTS.md` stays, since every game session reads it as shared agent context (`shared_agent_context_path`); it keeps only what a game session needs and points at the repositories for development, and the switchover moves it with the runtime state into `%LOCALAPPDATA%\Pluri-Bot`, where v1-1's `shared_agent_context_path` names it.

## Step 2: v1-1 and GitHub Releases

### Update source

From v1-1 the engine looks for updates in the latest release of `astenlund/DLSS5-Bot`. It accepts a release only when all of these hold: it is the release GitHub marks as the repository's latest, which the publish step always sets on the release it publishes, neither draft nor prerelease; its tag is the pair embedded in the attached package; it has exactly one asset named `DLSS5-Bot.cmd` and exactly one named `DLSS5-Bot.cmd.sha256` (other assets are ignored, so later releases can add files without breaking older engines); the `.cmd` asset is within the existing 4 MiB size bound and its bytes match the `.sha256` asset, and also match the digest the API reports for the asset where it reports one; the bytes are a DLSS package in published form, the check the gist path makes today; its mission declares the file name `DLSS5-Bot.cmd`; and they carry neither the engine mark nor the local mark. The release text is never a hash source. The accepted release is then applied as Updating describes.

Every refusal leaves the copy as it was and is recorded in an update failure category, with the specific reason saved in the failure record's existing message field, which today always holds a generic text, so that two different refusals leave the author two different diagnostics.

The asset download follows a redirect only over HTTPS and only to the GitHub-owned hosts that serve release assets; any other redirect is refused, as every other GitHub request already refuses redirects. That allowlist is a recorded tradeoff: should GitHub move release assets to another host, auto-update stops on every copy until each is replaced by hand, which the single author accepts. The exact API surface (the endpoints, the digest the API reports for an asset, the asset hosts, and the latest-release endpoint's treatment of drafts) is to be verified against GitHub's REST documentation during implementation (provisional citation). Pluri-Bot and DLSS5-Bot enable GitHub's immutable releases where the account offers them, as a safeguard the engine does not depend on.

Rate limits, timeouts and offline behavior keep the gist path's handling. The gist reading code is removed from v1-1.

### Stage writes

The stage write is a sequence of writes, the staged command before its stage record, and today a stop between them leaves a state that reads as blocked on every later attempt until the user moves the files aside. v1-1, which rewrites the stage writer for Releases, recognizes under the bootstrap lock the states such a stop leaves (a staged command without its record, and a new command beside the previous record that no longer matches it) and resumes by discarding the leftover command so the next fetch stages again, but only when the leftover command's bytes match a hash this machine trusts for its version, which the writer records before it replaces the command. A file at that path whose bytes it cannot prove that way is kept, and the state stays blocked with today's recovery message. The mission's cleanup boundary is brought into agreement with this authority and with the stage record v1-1 writes.

### The gist after the reset

No package is published to the gist again. After the switchover, the gist's README is replaced, in one write the user approves, by a pointer at the DLSS5-Bot releases page saying that the gist is frozen at legacy v67. The write first confirms that the gist is still at the revision legacy v67's publication recorded, changes only the README, and then reads back from the resulting revision that the README is the pointer and `DLSS5-ADDER.cmd` still has the legacy v67 hash. The gist's `DLSS5-ADDER.cmd` thus stays the legacy v67 bytes, so the gist offers a legacy copy nothing newer; what a legacy copy on this machine does after the switchover is set out in Switchover on this machine. The gist is never deleted. `astenlund/DLSS5-Bot` is never renamed, transferred or deleted, since every copy from v1-1 on reads it and refuses redirects; a move would be a migration like this one, and DLSS5-Bot's `AGENTS.md` and README say so.

### Switchover on this machine

The switchover is how the new line first arrives on any machine that holds legacy copies, this one being the only one known, and runs the same way on each; a new-line copy is not placed on such a machine before its switchover. The switch from legacy v67 is made by hand, with the first new-line release that passes both its readback and its live check, normally v1-1; if v1-1 fails either and is superseded, the first successor that passes both takes its place in this section, in the release notes and in Step 2 acceptance, installing over whatever the new canonical slot then holds. In order: a copy of the release's verified bytes is placed in the old folder's canonical slot (`%LOCALAPPDATA%\DLSS5-ADDER\DLSS5-ADDER.cmd`), so that no launch of a legacy DLSS copy can seed or first-use legacy trust from then on (a legacy package of another mission is the exception the next paragraph sets out), unless an earlier new-line release's blocking copy is already there, which is kept, since any new-line bytes block equally; that copy only blocks, since no new-line engine reads the old folder and the file name its mission declares is not `DLSS5-ADDER.cmd`, so a launch of it is refused before it writes any trust. Its refusal tells the user to rename it, which must not be followed: renaming it empties the old slot, which a legacy launch would then seed again, as the next paragraph sets out. Then the legacy trust records are moved aside, both the trust entries and recorded maxima in `engine\ENGINE.md` and their mirror in the machine notes, a step done only when no legacy trust key remains in either file. Then the runtime state other than the canonical copy, the shared agent context and the knowledge file among it, moves with `release-records\` from the old folder into `%LOCALAPPDATA%\Pluri-Bot`, which must hold nothing the move did not put there, apart from the test-store marker in a rehearsal; the real switchover refuses a marker there, since it would let marked builds write trust in the real store. The move also refuses while the old folder's bootstrap lock is held or the folder guard of any game folder its location records name is held, probed on the guard itself rather than read from the holder records in `guards\`, and refuses when it cannot tell, so no open legacy session keeps writing notes or location records there after the move. Records in it that name paths under the old folder, such as the runtime build store's build records and its recorded Python runtime, are carried as they are: the local runtime build instructions already check a recorded runtime and its venv before use and acquire them again when a check fails, so a moved venv that no longer works is replaced rather than trusted. Then the release procedure's install puts the release in the new canonical slot (`%LOCALAPPDATA%\Pluri-Bot\DLSS5-Bot.cmd`), writing its trust into the fresh store; the live check runs; and the user replaces each game copy with the published package, removing its `DLSS5-ADDER.cmd` and that copy's `.bkp`, renaming its game notes to `DLSS5-Bot.md`, and committing the change where Git tracks the game folder; none of the copies holds an edited mission (the user's statement, 2026-11-21). Each step is guarded by the content it expects, so a stopped switchover continues from the first step not yet done. If the live check fails, the legacy trust stays moved aside and the failed release stays installed, so the author's legacy game copies refuse to start until a successor passes both checks and the switchover completes with it; that interval is accepted, since only the author's own copies are affected.

A legacy v67 DLSS copy launched afterwards cannot parse the blocking copy in its canonical slot, which has no legacy markers, and treats it as malformed: on a normal startup it prints its canonical recovery message, which tells the user to move the canonical copy aside, and then refuses to start, because with the legacy trust moved aside its own engine is no longer trusted. That message must not be followed: with the canonical slot empty and no legacy trust, the next legacy launch would seed v67 back into the canonical slot and write legacy trust again. The stale copy is replaced like the others. A Git-tracked copy that differs from its committed form stops earlier, at v67's Git gate (`Updater Git state blocks replacement`), before the recovery message: an armed copy does, since arming writes its STATE section into the file, and so does a copy with bare LF line endings, which first rewrites itself to CRLF, as v67 does on a normal game launch. A copy whose game folder has Git metadata but no git command, or one git cannot inspect, starts a diagnosis-only session, which refuses for want of trust without printing the message; in every case the remedy is the same. A legacy package of another mission, such as the v67 hello-world base, differs: it treats the malformed canonical copy as absent and, once the user accepts its trust prompt, writes legacy engine trust, after which a stale v67 DLSS copy would run again. So no legacy package of any mission is launched against this machine's real store after the switchover (the isolated test stores that run the legacy fixtures are unaffected), and a legacy trust prompt is declined. These branches are confirmed on the v67 code; older legacy versions are not examined and are not launched either.

### Release automation and publication order

Pushing a release tag runs a GitHub Actions workflow on a Windows runner. In Pluri-Bot it joins the engine and assembles the hello-world base from the tagged commit; in DLSS5-Bot it assembles the package from the tagged commit with the pinned engine. Each workflow creates the release as a draft, attaches the files and their SHA-256, refuses unless the built bytes' SHA-256 equals the reviewed and locally checked candidate's, recorded in the tagged commit, and, in DLSS5-Bot, unless the package's mission declares the file name `DLSS5-Bot.cmd` and the candidate's pair is at least as high as the highest pair among all published releases in both halves and higher in one, or, when the release listing reads successfully and holds no earlier release, has mission version 1 and the engine of the first new-line Pluri-Bot release, `legacy-v67` excluded, that passed its own readback and was not superseded before any DLSS release (normally v1-1, or v2-1 when Pluri-Bot v1 was superseded, for a failed readback or a defect found later); a release listing that cannot be read refuses. A workflow whose checks all pass leaves the release a draft: publishing it is a separate step the user approves, at which those checks run again, and that final check and the publish run exclusively of every other DLSS publication run, so a retried or stale candidate can never take a pair another release used and of two candidates for the same successor at most one publishes. No incomplete or unapproved release ever becomes the latest. A published DLSS release is never deleted: a bad one is superseded by a later release, so a published pair is never reused, while a draft can still be removed. Every DLSS package is published disarmed with an empty `STATE` section, as today. Assembly must be deterministic; the implementer confirms it by assembling on the runner and locally from the same commit. The full post-review suite stays a local run until the Release suite in CI draft is taken up.

A release proceeds in this order: the Pluri-Bot engine release when the engine changed, then the DLSS5-Bot tag and its workflow, then the approved publication of its draft, then a readback of the published asset against the reviewed hash, then the install of the canonical copy here from exactly those bytes, with trust written as today, then the live check, in which the installed copy's own reader reads the published release, through the same discovery, tag, asset, checksum and redirect handling other copies use, and finds it current. Since the reader runs today only as a game session's background worker and the canonical copy never runs a session, the check runs through an internal entry point of the canonical copy that reads and verifies the latest release and stages, applies and writes nothing, so it needs no game copy and makes no first use. Installing only after the readback means a candidate refused at publication leaves no trust on this machine. For the first new-line release, the install is part of the switchover. Each destination's guard checks that destination's own last verified content, so the release record keeps the last published release and the last verified canonical bytes separately: after a v1-1 superseded for its readback they differ (v1-1 published, the new canonical slot still empty, legacy v67 in the old one), after one superseded for its live check the slot holds v1-1, and in either case the successor installs over whatever the record says the slot holds. Each partial state resumes as follows:

- A tag pushed whose workflow fails before publishing leaves nothing auto-update can see: the release stays a draft, though the pushed tag itself is public. A transient failure reruns the workflow on the same tag; a hash refusal means the tagged commit is wrong, so the draft and the tag are removed, the tag deletion confirmed by the user, and the release is redone.
- A published release whose readback fails stops the release: nothing is installed, and the user decides; the release stays published, and if it is bad a later release supersedes it.
- A live check that fails after the install stops the release the same way: the installed copy stays, as a published release whose bytes passed readback, and the release that supersedes it installs over it.
- A retry that finds a destination already holding the intended bytes keeps it and continues; other bytes there stop the release.

### Release procedure from v1-1

The release procedure in DLSS5-Bot's `AGENTS.md` replaces the gist write with the tag and release, keeps every other step (candidate, verification, test before review, review, full checks, install, verify, record, backlog) with the install moved after the release readback, as the order above sets, and records the published release's tag, commit, pair and asset SHA-256 where it recorded the gist revision.

## Branches this design leaves to the default

Every conditional above has an empty and a fallback branch. Where one is not spelled out, an undefined branch is an omission, not a deferral, and when no user is available to settle a boundary the mechanism refuses with its existing error or skips with a recorded note.
