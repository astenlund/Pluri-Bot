# Spec review triage (round 1: Astra and Fable)

Decided dispositions; spec edits are deferred until triage ends. Entries before the rename name the repositories by their earlier names, Pluribot and dlss5-adder. Paths under `development\` name the frozen local archive in the LocalAppData folder the project came from; they are not part of this repository.

1. Headless absorb cannot produce the published package (both reviewers). Decision (user, 2026-11-20): Pluribot ships in exploded form. Its source is split: a batch wrapper plus `payload.ps1`, joined at build time into the engine file (the package with empty MISSION and STATE section bodies), whose SHA-256 equals the engine hash trust records; plus the hello-world mission as loose files, the assembled hello-world base being a build product. dlss5-adder vendors only the engine file, and its pin records the engine version, the Pluribot tag and commit, and the engine hash. Assembly embeds the DLSS mission folder with an empty STATE section through the package's own section functions, never through absorb. The feature record's "vendored copy of the base .cmd" and "running absorb headless" are amended to match.
2. The v68 double publication has no order or partial-state resume (both reviewers). Decision (user, 2026-11-20), accepted as proposed: order is the Pluribot engine release, then the dlss5-adder tag, whose workflow creates the release as a draft, attaches the `.cmd` and its SHA-256, verifies the hash and only then publishes it, then a readback of the downloaded asset against the reviewed hash, and only after that the gist write. Every release, not only v68, stays a draft until complete (the latest endpoint skipping drafts is provisional). Resume: tag pushed but workflow failed before publishing, nothing is user-visible; a transient failure reruns the workflow on the same tag, a hash refusal removes the draft and the tag (tag deletion confirmed by the user) and the release is redone; release published but readback fails, stop, no gist write, the user decides; gist written without a release cannot occur by the order; a retry finding a destination already holding the intended bytes keeps it, other bytes stop the publication.
3. Historical packages the suite reads stay in the archive (both reviewers). Decision (user, 2026-11-20), accepted as proposed: the v22 and v49 packages read by `tests\Test-DLSS5Package.ps1` are committed to dlss5-adder as fixtures under `tests\fixtures\` with their SHA-256 (already public in the gist history; still covered by the privacy sweep); the standalone v23 and v24 suites and the v23 delegation in `Test-DLSS5Adder.ps1` are retired, with the reason in the import's record; the baseline and interop runs obtain the previous release's bytes by reassembling the previous tag or downloading its asset, verified against that release's published hash, except v67, which was never a release and is committed as a fixture with its recorded SHA-256; acceptance runs the retained suite with the `development\` archive unavailable.
4. Stage records across engines (both reviewers). Decision (user, 2026-11-20), option A: v68 writes a stage record every older engine in use accepts: `schema_version` 1, the gist owner and id fields at their constant values, `gist_revision` holding the release's tagged commit (40 hex), and added fields naming the real source (repository, tag), which v67's parser tolerates (it refuses only duplicate or case-variant names). The implementer confirms no older engine uses `gist_revision` beyond its format check; compares the stage reader and its consumers (adoption, cleanup, the launch recovery message) across every release from the first with `stage.json` through v67 and records one case per distinct reader; and adds an interop case in which v68 stages from a recorded release response and a v67 copy launches and adopts it. The mission's cleanup boundary keeps working unchanged.
5. Mission-only releases have no versioning rule (Astra). Decision (user, 2026-11-21), replacing the proposed bump-only Pluribot releases, which the user rejected as backwards: a package is identified by the pair `v<engine>-<mission>`, the engine version owned by Pluribot and the mission version owned by the mission's repository, both starting at v68-68. Each number maps to one set of bytes (engine version to engine hash, mission version to mission hash); engine trust keys on the engine version, whole-file trust on the pair. Each half is ordered and updated independently: a copy takes the release's engine when its engine version is higher, and is offered the release's mission (Take or Merge, as today) when its mission version is higher; neither half goes backwards, and no combination such as v69-68 next to v68-69 is refused. A copy can therefore end on a pair never released, a local combination like an engine-only update of an edited mission, with no whole-file trust record. This rests on the property that an engine runs every mission an earlier engine ran, stated once in the spec, with no minimum-engine field. Older engines, which read the two legacy version markers, require them equal and compare one integer, see a hidden release ordinal stamped into both markers by the assembler: 68 for v68-68, then one higher per DLSS release in publication order. Display (menu header, what's-changed box, README) and release tags use the pair, and the release check compares the tag with the embedded pair. Pluribot's hello-world base carries its own pair with its own mission numbering.
6. The stage write's crash recovery is overstated (Astra); pre-existing in v67. Decision (user, 2026-11-21), option A: v68, which rewrites the stage writer, recognizes under the bootstrap lock the two states a stop between the staged command write and the `stage.json` write leaves (a staged command without metadata, and a new command beside the previous metadata that no longer matches it) and resumes by discarding the orphaned command so the next fetch stages again. It acts only on positive evidence that the files in the engine-owned `updates\` folder match one of those two shapes; anything else stays blocked with today's recovery message. Older engines still read such a state as blocked until a v68 copy launches. The spec's "crash-consistent as it is today" wording is corrected.
7. Trust recording is overstated (Astra, confirmed at engine lines 6602 and 6623). Decision (user, 2026-11-21): wording only, no behavior change: trust records the hash of each pair this machine stages, and a later fetch of a recorded pair with other bytes is the existing integrity collision; immutable releases stay a safeguard the engine does not depend on.
8. The gist migration promise is too broad (Astra, confirmed by `development\v24\HANDOFF.md`). Decision (user, 2026-11-21): the promise is narrowed to copies from v24 onward, which update to v68 through the gist while GitHub serves API version 2022-11-28 (engine line 6549); copies before v24, and any copy once that API version is retired, cannot. Their route is manual: the frozen gist's README points at the dlss5-adder releases page and the user replaces the copy with the downloaded package, the replacement route the project already supports for copies too old to repair themselves. No new mechanism.
9. Pluribot's own release is undefined (Fable). Decision (user, 2026-11-21): Pluribot tags `v<engine>` (such as `v69`) and dlss5-adder tags the pair (such as `v69-68`); Pluribot's release workflow follows dlss5-adder's rules (draft until complete, hash checked against the reviewed engine, then published). An engine candidate is reviewed and run through dlss5-adder's full checks from the local Pluribot tree, and Pluribot tags it only after they pass, the tagged engine hashing identically to the tested one. An engine fix after a tag takes a new engine version; a tagged engine version is never republished with other bytes. Step 1 pins a Pluribot `v67` release of the v67 engine, so the pin and update script are proven before v68; the pair numbering starts at v68-68.
10. The asset and hash contract is ambiguous (Fable, minor). Decision (user, 2026-11-21): a release has exactly one asset named `DLSS5-ADDER.cmd` and exactly one named `DLSS5-ADDER.cmd.sha256`; none or several of either is refused, and other assets are ignored so later releases can add files without breaking older engines. The `.sha256` asset is required and the downloaded bytes must match it; where the API reports a digest for the asset it must match too (a mismatch is refused, an absent digest is not, the field being provisional). The release body is never a hash source.
