# Pluri-Bot

Pluri-Bot is the engine of a composable AI bootstrap: one self-contained `.cmd` package that carries a shared engine and the mission content of one task. The engine started as DLSS5-ADDER's bootstrap, and the DLSS mission now lives in its own repository, [DLSS5-Bot](https://github.com/astenlund/DLSS5-Bot), which vendors this engine. Deferred ideas are tracked as Exploring drafts in `.nightshift/FEATURES.md`; those entries are not approved work, so do not implement them unless the user explicitly asks.

## Layout

- `engine/wrapper.cmd` and `engine/payload.ps1` are the engine's source. The wrapper is the batch block, the empty `MISSION` and `STATE` section markers and the two payload markers on adjacent lines; `payload.ps1` holds the PowerShell payload between them, exactly as the engine file carries it. `tools/Join-Engine.ps1` joins them into the engine file, a package with empty `MISSION` and `STATE` sections, so the engine file's SHA-256 is the engine hash of every package assembled from it.
- `missions/hello-world/` holds the hello-world mission as loose files, the layout Explode writes. `tools/Build-Release.ps1` joins the engine into `build/engine.cmd` and assembles the hello-world base from it into `build/DLSS5-ADDER.cmd`, each with a `.sha256` file; a Pluri-Bot release publishes those files. The base keeps the file name `DLSS5-ADDER.cmd` because the legacy v67 engine runs a package only under that name; from v1 each mission declares its own file name.
- Assembly runs through the carried `tools/Assemble-Package.ps1`, with `tools/Get-PayloadDefinitions.ps1`, until the engine's own `--internal-assemble` entry point replaces it in v1.
- `tests/Test-HelloBase.ps1` runs the base's own test headless without a console window, so it runs directly. `tests/Test-PluriBotBase.ps1` holds the release-suite cases that read the hello-world base; its helper functions are copied unchanged from DLSS5-Bot's release suite until the engine cases move here, and it opens console windows, so run it only through the off-screen runner: `tools/Invoke-SuiteOffscreen.ps1 -UpdaterPath <base> -OutputPath <file>`.
- `docs/repository-home/` holds the design of the move into these repositories and the record of its review decisions. `records/` holds the import's record.
- `.nightshift/` is the backlog for engine work and for work that spans the engine and a mission; the history indexes, including DLSS5-ADDER's, live here.

## Working rules

- Every source file is UTF-8 without a byte-order mark, ASCII unless a file says otherwise, with uniform CRLF line endings and one terminal newline; `.gitattributes` stores every file byte for byte. The engine's identity check refuses any other form of a package.
- Edit the engine in `engine/payload.ps1` or `engine/wrapper.cmd`, never in a built or vendored copy. A change that alters the engine bytes is a new engine and needs a new engine version.
- Run console-window tests only through the off-screen runner, under the PowerShell tool rather than Git Bash, never two runs at once, and after stopping a run run `tools/Invoke-SuiteOffscreen.ps1 -RestoreOnly` at once to restore the console host setting. Never let a test show windows on the user's screen.
- The engine's runtime state on a machine lives under LocalAppData, never in a clone.
- Before every push, run `tools/Invoke-PrivacySweep.ps1 -Range <outgoing range>` (for a first push, `-Range HEAD`); its literal terms live outside the repository, in the LocalAppData `release-records\sweep-terms.txt`, and a hit or a missing terms file stops the push.
- Releases: the `legacy-v67` release, made by hand, publishes the imported legacy v67 engine and its hello-world base. The release procedure for new-line engine releases, from v1, is set out in the repository-home design's Step 2 and is added here when that step ships.

## Engine behavior through legacy v67

DLSS5-ADDER's layout notes recorded what the engine does, release by release, as it carried the DLSS mission, and how a package's payload and mission files are inspected and where its machine state lives. The last two bullets describe the LocalAppData layout of that time: their release folder is a development archive folder there, and "here" and "this directory" in them mean the LocalAppData `DLSS5-ADDER` folder, never this repository:

- `DLSS5-ADDER.cmd` is a batch wrapper around a PowerShell payload between the `POWERSHELL_PAYLOAD_BEGIN` and `POWERSHELL_PAYLOAD_END` markers. From v50 it is a composable package: between the batch block's closing `)` line and the payload's begin marker it embeds a `MISSION` section (the mission files, each base64-encoded) and a `STATE` section (the arm state, any pending update record and, from v55, test records), and the published file has an empty `STATE` section. Launched without arguments it opens a menu, and after an update or on a new package a what's-changed box. Files dropped onto it are absorbed into its mission after confirmation, and a command-line task runs only on an armed copy, except that a diagnosis-only session starts whatever the arm state. The published package carries the `dlss5` mission: its `MISSION.md` template builds the game-session agent's operating prompt, which keeps its safety core inline and names four situational instruction files (cleanup boundary, settings optimization, local runtime build, bootstrap changes, held as `INSTRUCTIONS.<name>.md` mission files). The bootstrap writes those files to `prompts\dlss5-agent-sections-<prompt id>\` (the ID in the prompt file's name) at launch and removes them with the prompt file after the agent exits. In a normal session the `dlss5` mission runs the Git preflight, hardware probes, notes files, the startup snapshot of a non-Git game directory, and update and trust machinery before it launches Codex or Claude Code. When Git metadata exists but no git command is found (v46 and later), or git cannot inspect the repository (v48 and later), it starts a diagnosis-only session instead, which skips the Git preflight and the update machinery and blocks game changes until a normal relaunch. From v51 the menu's Configure item edits this machine's settings in `machine-config.json` (host, host path, per-host model and effort, the expected Claude account; `--host` and the `DLSS5_*` variables still override them per launch), the mission's project config (approval mode, rerun, target) and an optional `SEED.json` mission file; Execute refuses where the mission's declared target does not hold, and the `dlss5` target is a game executable within two folder levels. From v52 a single-instance guard, one named mutex per package folder, lets only one agent session, write of the copy, (from v55) test run, (from v57) store clear or (from v60) mission merge hold a folder at a time: a second one is refused at once and names the holder, and a startup update of a busy copy waits for a later launch. From v53 the engine keeps its own state in an engine store instead of the notes files: trust, and hardware and display probe results, in `engine\ENGINE.md`, and for each game directory a location record under `engine\locations\` holding the game identity, the session status, the display check finding and the agent's transaction marker, which the agent sets only through `--internal-location-set`. Machine notes keep a read-only mirror of the trust entries for older copies, and the game notes keep the game fingerprint as an origin stamp. From v54 a normal launch of a game copy that is valid apart from bare LF line endings (a Git checkout without CRLF conversion, or an editor save) rewrites it to its CRLF form under the folder guard and relaunches it with the same arguments (if Git tracks the copy, the repair must be committed before a machine that has not run v54 accepts it), also when the launch goes on to a diagnosis-only session, which still needs a machine that trusts v54; mixed endings, a doubled final newline and the shared AppData copy are still refused as damaged. A copy older than v54 cannot repair itself and must be replaced once. From v55 a mission can carry tests: `TEST.<name>.ps1` mission files declared in `PROJECT.json`'s `tests` field (each required or optional, with the dev or target role it runs at, and optionally target-only), run from the menu's Run tests item or `--internal-run-test`. Each result is a `test_record` line in the `STATE` section (which then carries `state_schema: 2`), holding the test name, verdict, role, mission hash, time, machine id, location hash and computer name and folder, never test output, and it travels with the copy, a whole-file update included. A mission with required tests arms, and Execute or a command-line task runs, only while each required test has a matching pass on the current mission hash; every mission content write removes the records. The DLSS mission declares no tests and arms by confirmation. From v56 the menu's Remove mission files item, or `--internal-remove`, removes instruction and test files from a mission, each removed test's declaration with it, as a mission content write; `MISSION.md` and `PROJECT.json` are never removed, the seed only through Configure, and an instruction file the template still names is refused. From v57 `PROJECT.json` declares the mission's memory stores and post-run checks: `stores` names the slots (`target`, `machine`, `knowledge`), each with a format, keyed for the `dlss5` mission and free-form Markdown for any other, and `post_run_checks` names built-in checks, today only `display-targets` for the `dlss5` mission; an absent field keeps the mission's historical meaning (all three keyed stores and the check for `dlss5`, nothing for any other). A session creates, reads and validates only the declared stores, apart from the compatibility operations on the machine notes and the check for a legacy transaction marker in the game notes, and the template's `{{stores}}` placeholder renders the rules for the declared stores. The menu's Stores view lists the declared stores, apart from the target store on the shared AppData copy, and can open or clear each one that exists. From v58 a mission that declares any store refuses a Windows device name (`con`, `prn`, `aux`, `nul`, `com1` to `com9`, `lpt1` to `lpt9`) as its `mission_id`, because a store path built from such an id can resolve to the device; the strict reading refuses it, so a v58 engine reports such a package as damaged and none of its writers produces one; a package on an earlier engine is unaffected, since only the DLSS package updates its engine. From v59 an update applied by a v59 or later engine to a DLSS copy whose published form is not this machine's record for its version (an edited mission) keeps the copy's mission files and test records, marks the copy as edited and replaces only the engine, disarmed, after the release's own engine accepts the result through `--internal-check-package` (run from a scratch folder in `updates\`; later engines must keep that command, since the older engine applying an update relies on it); a refusal or a check that cannot run skips the update and leaves the copy as it was. Its what's-changed box then offers the release's mission when it differs from the one the edit replaced or that one is unknown, and taking it is a mission content write that keeps the edited file as the `.bkp`. An unedited copy still updates whole-file, and so does an edited copy that a v58 engine updates. From v60 the box offers Merge with the release's mission wherever it offers Take: the AI host this launch selects merges the copy's edited mission with the release's, given the mission the edit replaced when this machine keeps it (a three-way merge, otherwise two-way), in a scratch folder under the folder guard, and the engine validates the result, shows what changed against each side and writes it only after the user confirms, as a mission content write that keeps the edited file as the `.bkp` and records the release's mission as the one the edit replaced (a result that, with the copy's own seed, equals the release's mission is written as Take writes it). From v60 a copy's first mission content write, when it records the published mission it replaced, keeps that mission on this machine as an ancestor, and so does a merge that is not written as Take, for the release's mission; ancestors never travel with a copy, and the Stores view lists, opens and clears them. From v61 the game fingerprint (a hash of the Steam app id, the folder name and the names of the qualifying executables at the top of the game folder) tolerates executables added to the folder: a location record or game notes holding the fingerprint over a subset of the current executables (any subset while there are at most ten of them, beyond that the sets with one or two removed, and always the eight largest) is accepted and kept as it is rather than widened, so the game still matches once an added executable is removed again, and a session other than a task session brings the game notes to the fingerprint its location record keeps. From v63 a location record with a `game_name` that names another game by that name or its `steam_appid` skips that subset search, and the search runs in compiled code. From v64 a trusted game copy also takes `--internal-notes-validate`, with no argument, which runs what its mission's default session end runs (for the `dlss5` mission the game notes read and declared post-run checks, for any other mission the free-form store check) without writing anything or taking the single-instance guard, and prints one JSON line naming the outcome: pass, finding (an incomplete selection, with its findings) or damage (stores that session end would fail to finalize, with the error), and from v65 missing (no game notes file, which a session started with a task never creates); the shared AppData copy refuses it. The DLSS mission requires the agent to run it after every game-notes write and before its final completion report, and asks for each `last_checked` as a date and time with offset. Most behavior changes are mission changes.
- The mission's source files live in the release folder's `mission-dlss5\`, and its `Assemble-Package.ps1` embeds them; `--dump-payload` recovers them from any package. Mission text is not interpolated, apart from the template's `{{placeholder}}` values, so it names state-block keys such as `dlssnr_patcher_store` instead of payload variables. `DLSS5-ADDER.cmd --dump-payload "<folder>"` writes the payload exactly as it runs (the text between the payload markers without leading or trailing blank lines; the reported SHA-256 is that of the file on disk) as `DLSS5-payload.ps1`, plus from v50 each mission file under its own name (from v41 to v49, each decoded prompt section as `DLSS5-<name>.md`), into that folder (created if missing; it refuses, writing nothing, if any of those files already exists), for inspection only: edits to the dumped files do not flow back into the bootstrap.
- The LocalAppData `DLSS5-ADDER` folder, where the canonical copy lives, also holds game-session machine state that is not project source: `machine-config.json` (from v51, with `machine-config.json.bkp` after a reset of an invalid file), `guards\` (from v52, one holder record per package folder whose single-instance guard is or was held, which only informs a refusal; a stale record is harmless), `engine\` (from v53, the engine file and the location records; the menu's Stores view opens the engine file and this location's record, and removes orphaned, unreadable or refused location records only after confirmation; from v60 also `engine\mission-ancestors\`, one file per mission an edit replaced, which a merge compares against and the Stores view can clear), the notes files, `dlssnr-patcher\` (the local runtime build store from v39, which from v47 can also hold a managed Python runtime and its venv), `prompts\`, `sessions\`, `snapshots\` (per-launch startup listings of non-Git game directories, from v45), `mission-tests\` (from v55, one scratch folder per test being run, removed when that test ends; one left by a failed removal or an interrupted run is harmless scratch that nothing reads), `missions\` (from v57, the machine and knowledge stores of missions other than `dlss5`, one folder per mission id, which also holds that mission's launch prompt files), and `updates\` (which from v60 also holds a `mission-merge-<id>` scratch folder while a merge runs; one kept after an agent exit that could not be confirmed, or a failed removal, is harmless scratch that nothing reads). Explode run from the shared copy here also writes the mission files (`MISSION.md`, `PROJECT.json`, `INSTRUCTIONS.*.md`, and from v55 any `TEST.*.ps1`) into this directory; they are scratch for editing, not project source. `test-runs\` holds release-suite and launcher test scratch, except `console-delegation-restore.json`, which is recovery state for the user's console-host setting and must never be deleted as scratch.
